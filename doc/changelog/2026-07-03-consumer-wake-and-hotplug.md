# 2026-07-03 — Пробуждение по потребителю + переживание hotplug камеры

## Почему

Сценарий отказа: пользователь переподключил веб-камеру, затем открыл браузер, но виртуальная камера
**не активировалась** — приложение не увидело изображение, помог только рестарт сервиса. Две независимые
причины:

1. **Детектор потребителя был fail-closed при EACCES.** Процесс, держащий `/dev/video10` из песочницы
   (Chrome запускает захват в non-dumpable дочернем процессе → его `/proc/<pid>/fd` недоступен, EACCES),
   не атрибутировался обходом `/proc`, и детектор считал, что потребителя нет → демон оставался в idle.
2. **Resume был слабейшим звеном реакквайра.** При выходе из idle демон вызывал `input.start()` на
   pipeline с прибитым путём и при провале молча оставался в placeholder навсегда — воркер об этом не узнавал.

## Что изменилось

- **Детектор: net-count latch.** Присутствие потребителя теперь определяется по балансу inotify-открытий
  `/dev/video10` (`IN_OPEN` +1, `IN_CLOSE_*` −1), а `/proc`-обход служит авторитетным якорем, когда он
  читаем. Открытие, которое невозможно атрибутировать (EACCES), но с положительным балансом — будит демон
  (**wake-on-any-open**: любой открывший устройство на миг активирует его; краткий probe `[OPEN,CLOSE]`
  даёт нулевой баланс и не будит). Устойчивое EACCES-«шумовое» присутствие root-демонов, не открывающих
  video10, idle больше не ломает.
- **Resume: `InputPipeline::reacquire()` + самовосстановление.** Возобновление теперь делает
  `Null → Playing` на существующем pipeline (переоткрывая устройство). При **устойчивом провале**
  реакквайра воркер чисто перезапускает конвейер, и авто-выбор устройства (`device = "auto"`) выбирает
  камеру заново — включая случай, когда после переподключения камера получила **другой** узел
  `/dev/videoN`. Ручной рестарт больше не нужен.
- **Метрики: единый источник строки.** Обе метрик-строки (периодическая и итоговая при завершении)
  печатаются из одной функции — новый счётчик добавляется в одном месте, и раньше «немые» счётчики
  (idle/acquire) теперь видны в обеих. Новые счётчики: `resume_failures_total`,
  `unattributable_wakes_total`. **Строки метрик теперь под таргетом
  `fluxframe::metrics`** — фильтр `RUST_LOG=fluxframe=…` их по-прежнему ловит, но узко-привязанные к
  `fluxframe_cli` фильтры/скрейперы перестанут матчить. **Итоговая строка (`"run metrics"`) сменила
  ключи** на суффикс `_total` (`frames_in` → `frames_in_total`, `fallback` → `fallback_total`,
  `effect_err` → `effect_err_total`, `frames_dropped` → `frames_dropped_total`) — теперь совпадают с
  периодической строкой (`frames_in`, `frames_out`, `frames_dropped`, `fallback`, `effect_err` →
  `*_total`); скрейперы, парсившие старые ключи итоговой строки, надо обновить. Итоговая строка теперь
  также несёт нулевые `fps`/`window_secs`/`*_delta` (у неё нет rolling-window).

## Действия оператора

Пересобрать и перезапустить сервис. Новых обязательных настроек нет.

## Ограничения

- **Hotplug-восстановление — только для `input.device = "auto"`.** При фиксированном пути демон при
  провале реакквайра завершится (рассчёт на рестарт супервизора shepherd/systemd), т.к. переэнумерации
  устройств для фиксированного пути нет.
- **Кратковременный blip.** Восстановление после переподключения перезапускает конвейер — потребитель
  видит доли секунды placeholder, как и при mid-stream unplug.
- **Разные счётчики про «не стартовал вход».** `resume_failures_total` (провал `reacquire` при resume) и
  `input_acquire_failures_total` (провал сборки+старта в `run_auto`) считают разные пути — не двойной счёт.
